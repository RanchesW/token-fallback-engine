# token-fallback-engine

Сервис принимает заказ на генерацию, списывает токены и отдаёт задачу провайдеру. Если провайдер отказал, задача уходит на следующую ногу, а если отказали все, токены возвращаются.

Стек: Python 3.12, FastAPI, asyncpg (сырой SQL), PostgreSQL 16, Alembic.

## Запуск

```bash
docker compose up --build
```

Поднимаются:

| сервис    | порт | что это |
|-----------|------|---------|
| `db`      | 5432 | PostgreSQL (`app` / `app`) |
| `migrate` | —    | `alembic upgrade head`, отрабатывает и выходит |
| `app`     | 8000 | сервис, `uvicorn --workers 4` |
| `alpha`   | 9001 | фейковый провайдер |
| `beta`    | 9002 | фейковый провайдер |

`app` стартует только после успешного `migrate`. Миграции вынесены в отдельный контейнер, чтобы четыре воркера не накатывали их наперегонки.

Пример:

```bash
python scripts/send_payment.py --user 1 --tokens 100      # оплата, она же создаёт пользователя
curl -X POST localhost:8000/generate -H 'content-type: application/json' \
     -d '{"user_id": 1, "model_slug": "image-fast", "prompt": "cat", "ref_images": []}'
curl localhost:8000/tasks/<task_id>
curl localhost:8000/users/1/balance
```

Переменные: `PROVIDER_TIMEOUT` (по умолчанию 60 с), `SUBMIT_TIMEOUT` (5 с на `POST /tasks`), `WATCHDOG_INTERVAL` (1 с), `WEBHOOK_SECRET`. Можно, например, запустить так: `PROVIDER_TIMEOUT=10 docker compose up`.

## Миграции

Миграции лежат в `migrations/versions`, внутри обычный SQL через `op.execute`.

```bash
alembic upgrade head                                  # применить (в compose это делает сервис migrate)
alembic revision --rev-id 0003 -m "add something"     # создать следующую: migrations/versions/0003_add_something.py
alembic downgrade -1                                  # откатить последнюю
```

`DATABASE_URL` берётся из окружения.

## Как устроено

```
users     баланс, это кэш суммы журнала
ledger    журнал: payment / charge / refund, у каждой строки уникальный op_key
models, legs   каталог
tasks     задача: статус running → completed | failed, план ног (снимок на момент создания)
attempts  попытки: submitting → waiting → completed | failed | superseded
payments  входящие оплаты
```

1. `POST /generate` в одной транзакции блокирует строку пользователя (`FOR UPDATE`), проверяет лимит в 3 активные задачи и баланс, создаёт задачу, пишет `charge` в журнал и первую попытку в статусе `submitting`. После коммита отвечает `task_id`.
2. Отправка провайдеру идёт в фоне. При ответе 202 попытка переходит в `waiting`, и от этого момента отсчитывается `deadline_at = now() + PROVIDER_TIMEOUT`. При 5xx, таймауте или обрыве соединения попытка получает `submit_failed`, и задача идёт на следующую ногу.
3. Вебхук, сторож и синхронная ошибка вызывают одну функцию `engine.settle_attempt`. Она решает, что делать дальше: следующая нога, `completed` или `failed` с возвратом.

Правила выбора ноги собраны в `app/routing.py`. `technical`, `submit_failed` и `timeout` ведут на следующую ногу. `moderation` тоже, но ноги со `skip_on_moderation` пропускаются. `payload` роняет задачу сразу.

## Почему «ровно один раз»

**Баланс равен сумме журнала, и это гарантирует база.** `users.balance` меняет только триггер на `INSERT INTO ledger`. Прямой `UPDATE users SET balance` триггер отклоняет (проверка `pg_trigger_depth`). Журнал append-only: `UPDATE` и `DELETE` запрещены. `CHECK (balance >= 0)` не даёт уйти в минус. Получается, что операции без строки в журнале быть не может.

**Начисление.** `INSERT INTO payments ... ON CONFLICT DO NOTHING`, затем `SELECT ... FOR UPDATE` на строке оплаты. Двадцать одновременных доставок выстраиваются в очередь на этом локе. Первая видит `credited_at IS NULL`, начисляет и ставит `credited_at`. Остальные видят, что оплата уже зачислена, и отвечают `duplicate`. Начисление происходит только при `status = "succeeded"`, другие статусы просто записываются. Если тот же `payment_id` придёт с другой суммой или другим пользователем, ответ будет 409.

**Возврат.** Любое изменение задачи (вебхук, сторож, ошибка отправки) идёт в транзакции, которая держит `SELECT ... FROM tasks FOR UPDATE`. Под локом попытка перечитывается. Если она уже закрыта, событие считается дублем и ничего не делает. Из десяти одновременных `failed` только первое застаёт попытку открытой, переводит задачу в `failed` и пишет `refund`.

Страховка на уровне базы:
- `ledger.op_key` уникален (`refund:<task_id>`), поэтому второй возврат упадёт с ошибкой и откатит транзакцию;
- триггер на `ledger` не даёт вставить `refund`, если задача не `failed`;
- триггер на `tasks` запрещает выходить из конечного статуса.

**Почему не `ON CONFLICT DO NOTHING` на журнале.** Баланс двигает BEFORE-триггер, а он срабатывает раньше проверки конфликта. Поэтому дубли отсекаются раньше: локом на оплате или переходом статуса задачи. Уникальный ключ нужен только для того, чтобы ошибка в логике падала, а не молча проходила.

**4 воркера.** Состояния в памяти нет. Сторож запущен в каждом процессе. Кандидатов он берёт через `FOR UPDATE SKIP LOCKED` и перепроверяет под локом задачи. Дедлайны сравниваются с `now()` базы, а не с часами воркера. Если два сторожа и вебхук придут к одной попытке одновременно, сработает только первый.

## Падение процесса посреди обработки

**Посреди обработки вебхука.** Вся обработка идёт одной транзакцией. Если процесс упал до коммита, Postgres её откатит, а провайдер не получит 2xx и пришлёт вебхук повторно (фейковый провайдер так и делает: ретраит на 5xx и сетевые ошибки). Если упал после коммита, но до ответа, повторный вебхук окажется дублем и ничего не изменит. Половины перехода, например «задача failed, а возврата нет», не бывает.

**Между коммитом и отправкой провайдеру.** Строка попытки в `submitting` работает как outbox. У неё есть `dispatch_lease_until`. Если воркер умер и не отправил задачу, после истечения lease сторож любого воркера отправит её заново. Повторная отправка безопасна, потому что запрос идёт с `Idempotency-Key = attempt_id`, и провайдер вернёт тот же `external_id`. Если это не получилось `MAX_DISPATCHES` раз подряд, попытка считается `submit_failed`. Тест: `test_resends_attempt_left_by_crashed_worker`.

**Вебхук пришёл раньше, чем мы сохранили `external_id`** (быстрый провайдер или падение сразу после 202). Провайдер возвращает в подписанном теле наш `client_ref`, то есть id попытки, и по нему попытка находится.

## Правило 6: поздний `completed`

Правило простое: побеждает первый конечный исход задачи, и деньги двигаются только при нём.

- **Задача ещё `running`.** Сторож сдался, и задача уже на следующей ноге, а возврата ещё не было. Поздний результат принимается: задача становится `completed`, текущая попытка на другой ноге получает `superseded`, а её будущие вебхуки игнорируются. Пользователь получает то, за что заплатил, и раньше. Отбрасывать готовый результат и ждать второго провайдера смысла нет.
- **Задача уже `failed`, и токены вернулись.** Результат не выдаётся. Задача остаётся `failed`, а URL сохраняется только в `attempts.result_url` для сверки с провайдером. В API он не попадает, в истории видно лишь `late_completed: true`. Забирать возврат назад (повторно списывать) нельзя: у пользователя может не хватить баланса, а молча списывать деньги по отменённой задаче — плохая практика.
- **Задача уже `completed` другой ногой.** Поздний результат игнорируется.

Гонку «поздний `completed` против `failed` последней ноги» решает лок задачи: кто первым его взял, тот и определил исход. Второй увидит конечный статус. Триггер на `tasks` не даст `failed` стать `completed`, поэтому результат и возврат вместе невозможны даже при ошибке в коде.

## API

| запрос | ответ |
|--------|-------|
| `POST /generate` | `202 {task_id}`. Ошибки: 400 (нет подходящей ноги, до списания), 402, 404 (пользователь или модель), 429. Необязательный заголовок `Idempotency-Key`: повтор вернёт ту же задачу без второго списания |
| `POST /webhooks/providers/{name}` | `{external_id, status, result_url \| error_type, client_ref}`, подпись `X-Signature` |
| `POST /webhooks/payments` | `{payment_id, user_id, tokens, status}`, подпись `X-Signature` |
| `GET /tasks/{id}` | статус, `current_leg`, `attempts` (провайдер, статус, тип ошибки, времена), `refunded` |
| `GET /users/{id}/balance?limit=20` | баланс и последние строки журнала с `balance_after` |

Подпись считается так: `hex(HMAC-SHA256(raw_body, WEBHOOK_SECRET))`. При неверной подписи ответ 401.

## Фейковые провайдеры

`fakeprovider/main.py` — одно приложение, запускается дважды с `PROVIDER_NAME=alpha|beta`. Поведение задаётся через `PUT /_admin/config` или начальной переменной `PROVIDER_BEHAVIOUR` (JSON). Сброс: `POST /_admin/reset`.

| поле | что делает |
|------|-----------|
| `delay_min`, `delay_max` | задержка вебхука, по умолчанию 2–20 с |
| `fail_rate`, `fail_type` | доля отказов и тип: `technical` / `moderation` / `payload` / `random` |
| `sync_error_rate`, `sync_error` | синхронный отказ: `503` или `timeout` (принять задачу и зависнуть на `sync_hang_seconds`) |
| `duplicates`, `duplicates_concurrent` | сколько раз слать вебхук, одновременно или по очереди |
| `drop_rate` | вебхук не приходит совсем |
| `late_rate`, `late_delay` | `completed` через `late_delay` секунд, позже нашего таймаута |

## Допущения

- Флаг модерации «липкий». Если в задаче хоть раз был отказ `moderation`, ноги со `skip_on_moderation` пропускаются до конца цепочки, а не только сразу после отказа. Технический сбой на промежуточной ноге не делает контент чище.
- Любой не-2xx ответ на `POST /tasks` считается синхронной ошибкой и ведёт на следующую ногу, а не `payload`. Сломанная интеграция с нашей стороны не должна ронять задачи пользователя окончательно.
- Неизвестный `error_type` в вебхуке считается `technical`.
- Регистрации нет: пользователя создаёт первая оплата.
- Цепочка ног фиксируется в задаче при создании. Правка каталога не влияет на уже запущенные задачи.
- Отмены у провайдеров нет. После `superseded` вторая нога доработает впустую.
